## 3. Теоретические сведения

Клиент-серверное приложение состоит из клиентской и серверной частей.

**Клиент** взаимодействует с пользователем и отправляет запросы серверу. В данной работе в качестве клиента используется десктопное приложение на Java Swing.

**Сервер** принимает HTTP-запросы, выполняет необходимую бизнес-логику, взаимодействует с базой данных и возвращает клиенту результат.

Для обмена данными используется HTTP, а данные REST API передаются в формате JSON.

В работе используется Basic Authentication. Клиент передаёт серверу данные авторизации в заголовке:

```text
Authorization: Basic <закодированные логин и пароль>
```

REST API позволяет клиентскому приложению получать и изменять данные сервера без прямого обращения к базе данных.

## 4. Серверная часть приложения

В качестве серверной части используется приложение Spring Boot, разработанное в предыдущих лабораторных работах.

Для работы с задачами используется сущность `Task`. Она содержит следующие основные данные:

- идентификатор задачи;
- название;
- описание;
- статус выполнения;
- дату создания;
- приоритет;
- категорию;
- пользователя;
- список подзадач;
- историю изменения состояния.

Связь задачи с пользователем реализована через `@ManyToOne`.

Для истории изменения состояния используется отдельная сущность `TaskHistory`, связанная с задачей.

### 4.1. REST API получения задач

На сервере реализован метод:

```java
@GetMapping("/api")
@PreAuthorize("hasRole('USER') or hasRole('MODERATOR')")
public ResponseEntity<List<Task>> getAllTasks() {
    return ResponseEntity.ok(taskService.getAllTasks());
}
```

Метод доступен пользователям с ролями `USER` и `MODERATOR` и возвращает список задач в формате JSON.

### 4.2. REST API добавления задачи

Для добавления задачи используется:

```java
@PostMapping("/api")
@PreAuthorize("hasRole('USER') or hasRole('MODERATOR')")
public ResponseEntity<Task> addTaskApi(@RequestBody Task task) {
    taskService.addTask(task);
    return ResponseEntity.ok(task);
}
```

Клиент отправляет объект задачи в формате JSON методом POST.

### 4.3. REST API удаления задачи

Удаление ограничено ролью `MODERATOR`:

```java
@DeleteMapping("/api/{id}")
@PreAuthorize("hasRole('MODERATOR')")
public ResponseEntity<Void> deleteTaskApi(@PathVariable Long id) {

    Task task = taskService.getTask(id);

    if (task == null) {
        return ResponseEntity.notFound().build();
    }

    taskService.deleteTask(id);

    return ResponseEntity.noContent().build();
}
```

При успешном удалении сервер возвращает HTTP `204 No Content`.

## 8. Получение задач в клиенте

В классе `TaskManagerForm` для взаимодействия с сервером используется `HttpClient`.

Для получения списка задач формируется GET-запрос:

```java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("http://localhost:8080/api"))
        .header("Authorization", "Basic " + encodedAuth)
        .GET()
        .build();
```

Ответ сервера преобразуется из JSON в список объектов `Task` с помощью Jackson:

```java
List<Task> tasks = mapper.readValue(
        response.body(),
        new TypeReference<List<Task>>() {}
);
```

После получения данных список задач отображается в графическом интерфейсе.

## 11. Удаление задачи из клиента

В клиенте реализована кнопка **«Удалить задачу»**.

Пользователь выбирает задачу в списке и подтверждает удаление.

Клиент отправляет DELETE-запрос:

```text
DELETE /api/{id}
```

При успешном удалении сервер возвращает:

```text
204 No Content
```

После этого клиент повторно загружает список задач.

Если сервер возвращает `403 Forbidden`, клиент показывает сообщение:

```text
У вас нет прав на удаление задач.
Удалять задачи может только MODERATOR.
```

Таким образом, ограничение доступа контролируется сервером, а клиент корректно обрабатывает отказ в доступе.

**Скриншот удаления из клиента**
